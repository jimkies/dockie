# Dockie Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A portable Windows app that stores Roblox accounts and launches many of them side by side, each in its own signed-in Roblox window.

**Architecture:**
- The Tauri 2 Rust backend owns everything: storage (DPAPI-encrypted cookies), Roblox web calls, the one-at-a-time launch queue, the multi-instance lock, a 1-second ticker (previews, titles, FPS restore, RAM trim) and the sign-in webview.
- The front end is plain HTML/CSS/JS, served from `ui/` with no build step. It talks to the backend only through `invoke` and events.
- The pure logic (Join parsing, launch links, FPS restore decisions, import/export, trim timing) lives in separate modules with unit tests. The Windows and network glue is checked in the final end-to-end task.

**Tech Stack:** Rust 1.99, Tauri 2.12, tauri-plugin-dialog 2, reqwest (rustls), serde/serde_json, `windows` 0.62.2, image (jpeg), base64, url, tokio, anyhow.

**Spec:** `docs/superpowers/specs/2026-11-18-dockie-design.md`

## Global Constraints

**Platform and build**
- Windows 10/11 only.
- `windows` crate **0.62.2** exactly. Use the `windows` skill for exact API paths and Cargo features.
- Tauri **2.12.x**. Product name `Dockie`, identifier `com.dockie.app`, main window label `main` with title `Dockie`.
- Release build: `npx --yes @tauri-apps/cli@2 build --no-bundle` produces `src-tauri/target/release/dockie.exe`. No installer, no updater.

**Data**
- Data lives in `%LOCALAPPDATA%\Dockie\`: `accounts.json`, `settings.json`, `state.json`.
- Every write goes to `<file>.tmp`, then is renamed over the original.

**Safety rules**
- Cookies are only ever sent to `https://*.roblox.com`.
- Never send keyboard or mouse input to a Roblox window. No `SendInput`, and no `PostMessage` of input messages.
- Never change `FramerateCap` unless an account override or the global default is set. Always put the user's value back.
- Anything that creates a window or reads webview cookies runs in an `async` command or a spawned task, never a sync command or event handler (wry #583 deadlock).

**Exact text**
- Roblox window titles: `Roblox · <username>`. Login window title: `Sign in to Roblox — Dockie`.
- Error and UI copy:
  - Row errors: `Needs sign-in` · `Roblox isn't installed` · `Couldn't get a launch ticket: <msg>` · `Window didn't appear within 60 s` · `Couldn't read this link` · `Couldn't take the multi-instance lock` · `Roblox blocked freeing RAM`
  - Warning bar: `Roblox is already running — extra windows can't open.`
  - Export warning: `This file gives full access to these accounts. Only share it with people you trust.`

**Timings and limits**
- Ticker 1 s; preview width 240 px, JPEG quality 70; window wait 60 s; trim after 10 s minimized, then every 300 s; startup check at most 4 accounts at once.

**Commits**
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A pasted cookie with surrounding whitespace, quotes or a leading `.ROBLOSECURITY=`** should be saved cleanly, with the `_|WARNING:…|_` prefix kept. (Task 6, `normalize_cookie` tests)
2. **Messy links** (surrounding whitespace or newlines, uppercase host, no scheme, `web.roblox.com`, extra query parameters) should parse the same as clean ones. (Task 2 tests)
3. **First run with no data folder** starts empty. **A corrupt `accounts.json`** gives an error, and Dockie never overwrites it. (Task 3 tests)
4. **Launching an account that's already running** focuses its window instead of opening a second one. (Task 10, `split_running` test)
5. **A Roblox settings file that's missing or has no `FramerateCap`**: the launch still happens, and nothing is written. (Task 4 test)
